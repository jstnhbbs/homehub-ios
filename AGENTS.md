## Project map

Beacon is a family household dashboard (routines, chores, meals/recipes, groceries, sleep logs, birthdays, notes, calendar, weather). It is **iOS-first**: the SwiftUI app in `ios/` is the product, and the Next.js app is its backend plus a thin web shell.

- **Backend** (`src/`): Next.js 16 App Router, Drizzle on Turso/libSQL (`src/db/schema.ts`), Better Auth (`src/lib/auth.ts`). Roles are `owner`, `parent`, `guest` (`src/lib/household-roles.ts`).
- **Mobile API** (`src/app/api/mobile/v1/*`): one route folder per module. Routes use the helpers in `src/lib/mobile/http.ts` (`requireMobileHousehold`, `requireMobileParentHousehold`, `handleMobileError`). `src/lib/mobile/dashboard.ts` builds the dashboard payload.
- **Guest permissions:** guests are "view and log", enforced on the server and covered by `src/lib/guest-permissions.test.ts` (it calls every mobile route as owner, parent, guest, and signed-out). Setup and shared data are parent-only via `requireMobileParentHousehold`. Guests can read everything, add a note (`POST /notes`), log activity (naps, routine step and chore and snack check-offs), edit their own profile and photo, and change their own layout preferences. Editing or deleting notes and every grocery change are parent-only. Invite codes follow the same rule: `serializeHousehold` sends `inviteCode` and `guestInviteCode` only to people who can manage the household (guests get empty strings, because older app versions decode both as required), since the parent code would let a guest recruit parents or promote a second account. The iOS views hide controls with `appState.canManageHousehold`, but the server is the enforcement point. When you add a mobile route, add it to the test table.
- **Sleep writes** (`POST /naps`, `PATCH /naps/[id]`) answer with the entry they created or changed as `nap`, next to the older `ok` and `id`, so the Sleep page shows it at once and reloads in the background (`NapsView.commit`). Older servers omit `nap`; the app then reloads before showing anything. A child can have only one running sleep: `nap_logs_one_active_per_profile_idx` (migration 0026, a partial unique index on `profile_id WHERE ended_at IS NULL`) settles the race the up-front check can't, and `guardActiveSleep` in `src/lib/naps/store.ts` turns the index's refusal back into the plain "already has sleep in progress" message. Any write that can leave a sleep running (insert, or an edit that clears `ended_at`) goes through it. Use `requireMobileContext` when a route needs both the user and the household, so the session is read once.
- **Invite codes and errors:** codes are 10 characters from `src/lib/invite-codes.ts` (older households keep their 8-hex codes, so lookups only normalise). Every join path calls `assertMayTryInviteCode`, which limits tries per account (10 per 15 minutes) and per address (40 per hour). `handleMobileError` turns Zod failures into one readable sentence, `RateLimitedError` into 429, and database or coding errors into a generic 500 with the detail only in the server log; a plain `throw new Error("message")` is still treated as a deliberate 400 message.
- **Recipe import** (`src/lib/recipes/fetch.ts`) is the only place the server fetches a URL a user supplied, so it is locked down: ports 80 and 443 only, no credentials in the URL, private and link-local addresses refused (`isPrivateAddress`, including IPv6 wrappers of IPv4), the check done inside the connection's own DNS lookup so it can't be raced, every redirect re-checked, and time and size capped (including after decompression). Keep new outbound fetches behind the same policy.
- **Check-offs** (`routines/toggle-step`, `chores/toggle`, `snacks/toggle`) take an optional `completed` and answer with the state they ended in. The app always sends the state it wants, so a retried request or two phones tapping the same item can't flip it back, and a repeat leaves the first person's credit in place (`applyCompletion` in `src/lib/completion-state.ts`). Without `completed` (older apps) the item is flipped as before. A chore's `periodKey` must be a date for a daily chore or an ISO week (`2026-W40`) for a weekly one. When adding a new check-off call, pass `completed`.
- **Crouton import** (`Import from Crouton` in the Recipes menu): the phone reads `.crumb` files (JSON) and sends only their text to `POST /recipes/import/crouton` in batches of 10; `src/lib/recipes/crouton.ts` maps them (units, fractions, ranges, sections, nutrition, tags) and `recipes.import_key` (`crouton:<uuid>`) makes re-imports skip what is already there. Photos are resized on the phone and sent one by one to `POST /recipes/[id]/image` (Vercel Blob; sniffed by content, not by the claimed type). Section headings are `## Heading` lines in ingredients/directions: render them with `RecipeLines.display` and keep them off grocery lists with `RecipeLines.items`.
- **Account deletion** goes through Better Auth's `deleteUser` (enabled in `src/lib/auth.ts`, wrapped by `DELETE /api/mobile/v1/account`). Its `beforeDelete` hook runs `detachUserFromHouseholds` (`src/lib/account-deletion.ts`), which blocks the only owner of a shared household and deletes or leaves households otherwise. The privacy page describes this, so keep them in sync.
- **Routine streaks** are computed on the server (`src/lib/streaks.ts` for the rules, `src/lib/streak-store.ts` to load them) and returned as `routineStreaks` in the dashboard payload; the iOS app only displays them and celebrates milestones. Steps carry a `created_at` so adding a step never erases an existing streak; older steps fall back to their first completion.
- **Who completed what:** routine and chore completions record `completed_by` (the user who checked it off). The dashboard and chores payloads return `completedAt` and `completedByName`; it is null for older completions and after that person deletes their account (foreign key `ON DELETE SET NULL`). The household export leaves it out.
- **Recipe tags** are a JSON array in `recipes.tags`. `src/lib/recipes/tags.ts` normalizes them (preset spelling, dedupe, limits) and suggests them from a page's category and the ingredients; the iOS copy of the rules is `RecipeTagHelpers.swift`, so change both together. Updating a recipe without a `tags` field leaves its tags alone, so older app versions do not erase them.
- **Birthdays and anniversaries** share `family_birthdays`, told apart by `kind` (default `birthday`; older clients that send no kind create birthdays). Anniversaries never link to a profile and count years in `upcomingAge`. The dashboard's `hasAnniversaries` covers every entry (not just the 45-day window) and drives the module's name, "Birthdays" or "Celebrations", via `CelebrationNaming` on iOS. The stored module id stays `birthdays`.
- **iPad dashboard row height** (`DashboardCardLayout.rowHeight`) is the whole screen's height divided by the grid's total row count, shared across every card in that row. It is unrelated to any card's own content and only loosely related to the per-card Standard/Expanded size (which changes a card's *column span*, not its height). A card with more rows of content than fits gets clipped unless its content has its own `ScrollView`; every dashboard card does now (Meals was the one exception until it started clipping Dinner). `DashboardRowHelpers.swift` holds two small rules used across cards: don't repeat a value that's identical on every row (a native Reminders item's `category` is really just its Reminders list's name; a schedule row's calendar name is only worth showing once more than one calendar is in play).
- **Snacks** are household-wide by default: one tap marks a snack eaten for everyone. `households.snacks_per_child` switches to per-child tracking, where `snack_completions.profile_id` records which child ate it (`""` is the household-wide row, so it can sit in the primary key). Per-child only applies while the household has a child profile; with none it falls back to household-wide. The dashboard's `snackEaten` stays a flat label list for older app versions (in per-child mode a snack counts once every child has had it), and `snackCompletions` carries who ate what. The rules are in `snackEatenLabels` (`src/lib/meals/snacks.ts`) with `SnackHelpers.swift` as the iOS copy.
- **Web** (`src/app/`): every `(hub)/*` page except `settings` is an `IOSOnlyPage` stub. Real web pages are sign-in, onboarding, settings (household, profiles, members, photos), privacy, and terms. Server actions in `src/app/actions.ts` cover only household, profile, and photo management.
- **iOS** (`ios/HomeHub/`): `Models` mirror the schema, `Utilities` port logic from `src/lib`, `Services` hold the API client and on-device integrations (EventKit calendars, Reminders for groceries, WeatherKit, local notifications), `ViewModels` and `Views` are per module. There is also a widget under `ios/HomeHubWidget/`. The Xcode project is generated: after adding or removing Swift files, run `python3 ios/generate-xcode-project.py`. See `ios/README.md`.
- **Sleep Live Activity:** `HomeHubLiveActivity/` is a widget extension target (bundle id `com.jstnhbbs.beacon.liveactivity`, defined in `ios/generate-xcode-project.py`) that draws the lock screen and Dynamic Island timer. `SleepActivityAttributes.swift` is compiled into both the app and the extension, so keep it free of app-only types. `SleepLiveActivityManager.sync` reconciles one activity per active sleep and runs after every dashboard refresh and Sleep page load; activities are started locally (no APNs), so another device's nap shows up here only on the next refresh. The older `HomeHubWidget/` home-screen widget is still not a target.
- **Calendars are on-device only.** The server stores no calendar credentials or events. Anything named `calendarConnections`, `calendars`, or `calendarEvents` in the schema is unused legacy.
- **Schema changes:** hand-write the SQL in `drizzle/NNNN_name.sql` and add its entry to `drizzle/meta/_journal.json` (with a `when` greater than the previous one). Do not run `db:generate`: snapshots stop at 0007, so it would emit a bogus diff. Every statement in a file needs `--> statement-breakpoint` between it and the next, or only the first statement runs. `vercel.json` runs `db:migrate` before the build for production deploys only (`VERCEL_ENV=production`), so previews never touch the database. Migrations are the only way the schema changes: there is no runtime patching. `node scripts/check-migrations.mjs` (read-only) shows what `db:migrate` would run against `TURSO_DATABASE_URL`.

Checks: `npm run typecheck`, `npm run lint`, `npm test`, and an Xcode build of the `HomeHub` scheme for any iOS change.

## Cursor Cloud specific instructions

Standard commands live in `package.json` and `README.md` ("Checks" section); the notes below only cover non-obvious setup for running the backend in this VM.

- `.env.local` is gitignored, so it does not persist across fresh VMs. Create it before running the dev server: `cp .env.example .env.local`. `TURSO_DATABASE_URL` defaults to `file:local.db` and `BETTER_AUTH_SECRET` has a dev fallback, so the app boots even with empty secrets, but a real `.env.local` avoids surprises.
- The local SQLite DB (`local.db`) is gitignored and not created by `npm install`. Run `npm run db:migrate` once before `npm run dev` (migrations are intentionally kept out of the startup update script).
- Run the dev server with `npm run dev` (Turbopack) on port 3000. Do not use `npm start` for development. `npm run build:with-migrate` runs `db:migrate` first; plain `npm run build` does not.
- E2E tests (`npm run test:e2e`) use Playwright and need browsers installed first (`npx playwright install`, and `npx playwright install-deps` if system libs are missing). The Playwright config auto-starts its own dev server against `file:e2e.db`, so no manual server is needed for e2e.
- Core hello-world flow: open `http://localhost:3000` → Sign in → "Create an account" → complete `/onboarding` by creating a household → lands on `/settings`. Vercel Blob photo upload is an optional integration needing external credentials and is not required for local core testing.
