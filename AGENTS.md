## Project map

Tugboat is a family household dashboard (routines, chores, meals/recipes, groceries, sleep logs, birthdays, notes, calendar, weather). It is **iOS-first**: the SwiftUI app in `ios/` is the product, and the Next.js app is its backend plus a thin web shell.

- **The app's name** is Tugboat (it was Beacon, then briefly Porchlight; the tugboat icon and the name were chosen together). The visible name lives in `src/lib/app-info.ts` (`APP_NAME`, used by the legal pages and the web layout), the two `CFBundleDisplayName`s (`ios/HomeHub/Info.plist` and `ios/HomeHubLiveActivity/Info.plist`), and plain strings in the iOS views, the email templates and the web pages. **Deliberately still "beacon":** the UserDefaults and notification identifiers (`beacon.nativeCalendar.*`, `beacon.chore`, `beacon.nap`, `beacon.done`, `beacon.meal:`, the celebrated-markers), the `BeaconCache` folder, the `Beacon*.icon` bundles and `AppIconOption` names, `BEACON_WEATHERKIT_ENABLED`, the household export's `format` marker, and test temp-folder names. They are stored on devices or in files, so renaming them would reset people's saved settings or orphan scheduled reminders, and nobody sees them. The bundle ID (`com.porchlighthome.app`, still named for Porchlight because it is registered with Apple and cannot be renamed), its Keychain service name, the Xcode project (`HomeHub`) and package name are likewise unrelated to the display name.
- **Backend** (`src/`): Next.js 16 App Router, Drizzle on Turso/libSQL (`src/db/schema.ts`), Better Auth (`src/lib/auth.ts`). Roles are `owner`, `parent`, `guest` (`src/lib/household-roles.ts`).
- **Mobile API** (`src/app/api/mobile/v1/*`): one route folder per module. Routes use the helpers in `src/lib/mobile/http.ts` (`requireMobileHousehold`, `requireMobileParentHousehold`, `handleMobileError`). `src/lib/mobile/dashboard.ts` builds the dashboard payload.
- **Guest permissions:** guests are "view and log", enforced on the server and covered by `src/lib/guest-permissions.test.ts` (it calls every mobile route as owner, parent, guest, and signed-out). Setup and shared data are parent-only via `requireMobileParentHousehold`. Guests can read everything, add a note (`POST /notes`), log activity (naps, routine step and chore and snack check-offs), edit their own profile and photo, and change their own layout preferences. Editing or deleting notes and every grocery change are parent-only. Invite codes follow the same rule: `serializeHousehold` sends `inviteCode` and `guestInviteCode` only to people who can manage the household (guests get empty strings, because older app versions decode both as required), since the parent code would let a guest recruit parents or promote a second account. The iOS views hide controls with `appState.canManageHousehold`, but the server is the enforcement point. When you add a mobile route, add it to the test table.
- **Sleep writes** (`POST /naps`, `PATCH /naps/[id]`) answer with the entry they created or changed as `nap`, next to the older `ok` and `id`, so the Sleep page shows it at once and reloads in the background (`NapsView.commit`). Older servers omit `nap`; the app then reloads before showing anything. A child can have only one running sleep: `nap_logs_one_active_per_profile_idx` (migration 0026, a partial unique index on `profile_id WHERE ended_at IS NULL`) settles the race the up-front check can't, and `guardActiveSleep` in `src/lib/naps/store.ts` turns the index's refusal back into the plain "already has sleep in progress" message. Any write that can leave a sleep running (insert, or an edit that clears `ended_at`) goes through it. Use `requireMobileContext` when a route needs both the user and the household, so the session is read once.
- **Email confirmation:** `emailVerification` in `src/lib/auth.ts` sends a link at sign-up (24 hours, `sendOnSignUp`) and on request (`POST /api/auth/send-verification-email`, limited to 2 a minute). It is deliberately not required to sign in (`requireEmailVerification` stays off, so older accounts and slow email never lock anyone out), and following the link confirms the address without signing the browser in (`autoSignInAfterVerification: false`). Every link is rewritten to end on `/email-verified` (`verificationLink`, `src/lib/email-templates.ts`), a public page that also shows Better Auth's `?error=`. Email goes through `sendEmail` (`src/lib/email.ts`), which never throws: Resend when `RESEND_API_KEY` and `EMAIL_FROM` are set; otherwise nothing in production (a warning) and the server log in development (`outbox` in tests). Unconfirmed accounts get a reminder on the web settings page (`VerifyEmailNotice`) and in the app (`VerifyEmailCard` at the top of Settings only, not on Today, which refreshes the session when the app comes to the front). The link's host comes from `BETTER_AUTH_URL`, so that must be the real site URL in production. **Changing the email** (`POST /account/change-email`) in production only sends a link to the new address; the address changes when it is followed. The route answers `emailChanged` (true only when it changed at once, as in development for an unconfirmed address) and the app says "Check … for a link" otherwise. With no email provider in production (`canSendEmail` false) the change is refused, since no link could arrive. `src/lib/email-verification.test.ts` runs sign-up, link, verify and resend against the real Better Auth.
- **Invite codes and errors:** codes are 10 characters from `src/lib/invite-codes.ts` (older households keep their 8-hex codes, so lookups only normalise). Every join path calls `assertMayTryInviteCode`, which limits tries per account (10 per 15 minutes) and per address (40 per hour). `handleMobileError` turns Zod failures into one readable sentence, `RateLimitedError` into 429, and database or coding errors into a generic 500 with the detail only in the server log. Only messages written for people reach the app as a 400: a plain `throw new Error("message")` or a `UserFacingError` (`src/lib/errors.ts`; `BlockedUrlError` and `AccountDeletionBlockedError` extend it). Any other error class (a library's own, such as Vercel Blob's) or a system error with a `code` is a 500, so make a new error class that people should see extend `UserFacingError`. **One household per person:** creating a household, or joining a different one with a code, is refused for anyone already in one (`assertNoOtherHousehold` in `src/lib/household.ts`), because every screen shows only the first household joined; using your own household's code again is harmless. A household's time zone must be one the server knows (`isKnownTimeZone`), since every request uses it and there is no way to change it later.
- **Recipe import** (`src/lib/recipes/fetch.ts`) is the only place the server fetches a URL a user supplied, so it is locked down: ports 80 and 443 only, no credentials in the URL, private and link-local addresses refused (`isPrivateAddress`, including IPv6 wrappers of IPv4), the check done inside the connection's own DNS lookup so it can't be raced, every redirect re-checked, and time and size capped (including after decompression). Keep new outbound fetches behind the same policy.
- **Check-offs** (`routines/toggle-step`, `chores/toggle`, `snacks/toggle`) take an optional `completed` and answer with the state they ended in. The app always sends the state it wants, so a retried request or two phones tapping the same item can't flip it back, and a repeat leaves the first person's credit in place (`applyCompletion` in `src/lib/completion-state.ts`). Without `completed` (older apps) the item is flipped as before. A chore's `periodKey` must match its repeat (see **Chore repeats**): `once` for a one-off, an ISO week (`2026-W40`) for a plain weekly chore, a date for everything else. When adding a new check-off call, pass `completed`.
- **Chore repeats and times** (migration 0029; `src/lib/chores.ts`, `src/lib/chore-input.ts`, `ChoreHelpers.swift`): a chore repeats `repeat_unit` (`none`, `day`, `week`, `month`, `year`) every `repeat_interval`, has an optional `due_time` ("HH:mm", household time zone) and an optional `due_date`. For a one-off, `due_date` is the deadline (overdue once it passes, or once today's time has). For a repeating chore it is the **start date** the rule counts from (which weeks for "every 2 weeks", which day for monthly, never before it) and a repeating chore is never "overdue" for an earlier turn, only for today's time. Weekly takes its weekday from `days`; a daily chore can be limited to weekdays through `days` ("1,2,3,4,5"). Month and year use the start date's day, and the last day of a shorter month. Anything that counts from a date (every N days/weeks, month, year) needs one, and `resolveChoreSchedule` refuses without it. One-offs with no date stay on the list until done; a one-off done on an earlier day drops off the due list but stays in `scope=all`, and one can be ticked early (the app lets a one-off be, a repeating chore only on its day). Period keys: `once`, ISO week for week/1 (unchanged, so old completions still count), the date otherwise. **Older apps:** `cadence` is still written (`daily` for `day`, `weekly` for everything else) and the app still sends it, and requests with only `cadence`/`weekDay`/`dueDate` mean what they always did. Rows also carry `repeatUnit`, `repeatInterval`, `dueTime`, `nextDueDate`; the iOS `ChoreRepeatUnit` reads an unknown unit as daily instead of failing the whole list. The Repeat menu offers presets (`ChoreRepeatPreset`) plus Custom (every N days/weeks/months/years). A chore with a time gets its own local notification (`chore.<id>.<date>`, planned by `ChoreReminderPlanner`) and the rest share the evening check-in. The dashboard sends `upcomingChores` (timed chores on the next 3 days, `upcomingTimedChores`) so those reminders are scheduled before the day arrives, without the app being opened; today's come from `chores`. Settings → Notifications → Chores has "Timed Chores" (`choreLeadMinutes`, per device: at the time, or 5 minutes to 2 hours before); a reminder already inside its lead time fires at the time instead. The chore editor's delete button is a trash button pinned bottom-right of the sheet, away from Save, and asks first. The chore assignee picker lists only children, owners and parents (`Profile.canBeAssignedChores`, from `memberRole` on `GET /profiles`; the chore's current assignee stays listed when editing). `ios/checks/chore-helpers` and `src/lib/chores.test.ts` cover the rules.
- **Routine days and step order** (`src/lib/routines.ts`, `RoutineDays.swift`, `RoutineFormView.swift`): a routine has `days` ("1,3,5", 0 = Sunday) chosen with day chips in the editor (in the household's week-start order). The dashboard leaves out a routine's steps on days it doesn't run, so Today, the reminders and the check-offs only show what is on; the Routines page still lists every routine and shows "Not on today" for one that isn't. Streaks already honoured `days`. `POST` and `PATCH /routines` normalize `days` (`normalizeRoutineDays`, refusing none); `PATCH` without `days` (apps that predate day choices) leaves them alone. **Step order:** `PATCH` pairs the incoming labels with the existing step rows by label (`pairRoutineSteps`), so reordering moves a step with its row and its check-off history; before this it matched by position and a reorder would have relabelled rows. A reworded step takes over the leftover rows in order, as before. In the editor each step has a drag handle (press and hold, then drag; VoiceOver gets Move up and Move down), Return in a step's field moves to the next step or adds one after the last, and the remove button has a 44pt target. The delete button on the Chores and Routines editors is a corner trash button that ignores the keyboard (`.ignoresSafeArea(.keyboard)`) so it stays under it instead of riding over the fields. The Routines page groups cards by person (`RoutineGrouping`: household order, shared routines last, and through the day within a person: morning, after school, bedtime), with a name heading over each group when there is more than one. `ios/checks/routine-days`, `ios/checks/routine-grouping` and `src/lib/routines.test.ts` cover the rules.
- **Notification buttons (iOS, shown on the Apple Watch too):** a chore reminder carries a **Done** button and a "still asleep" nap check carries **End Nap**, so both can be handled from the lock screen or the watch without opening the app. `NotificationCommands` (Foundation only, `ios/checks/notification-commands`) owns the category names (`beacon.chore`, `beacon.nap`), the action names and the `userInfo` the buttons read (`choreInfo`, `napInfo`), and turns a button press into a `NotificationCommand` (nil for a plain tap, a dismiss, or a notification with missing ids). `NotificationResponder` (`Services/`) is the `UNUserNotificationCenter` delegate, installed in `HomeHubApp.init` so it exists when iOS launches the app in the background for a button press; it builds its own `HomeHubAPI` (the session cookie is in the Keychain, readable once the phone has been unlocked since boot), calls `toggleChore(completed: true)` or `endNap`, then posts `.homeHubDataChanged`, which `AppState` turns into a dashboard refresh. If the call fails it schedules a local notification (identifier `homehub.action.failed.<uuid>`) saying so rather than failing silently. The buttons use no `.authenticationRequired`/`.foreground` option, so they run in the background. `PlannedNotification` carries `category`, so `NotificationDiff` replaces a reminder that gains or changes its buttons. A new notification with a button needs: a category registered in `registerCategories`, info keys in `NotificationCommands`, and a decode case with a check. **Tapping a notification opens its page:** `request()` in `NativeNotificationService` stamps each reminder with a `destination` in its `userInfo`, worked out from its id (`NotificationCommands.destination(forNotificationId:)`: routine.* opens Routines, chore.*/chores.today Chores, sleep.* Sleep, birthday.* Celebrations; only those four are openable). A plain tap makes `NotificationResponder` keep the page and post `.homeHubOpenDestination`; `AppState.openPendingNotificationDestination` sets `selectedDestination` once the person is signed in with screens loaded (it is also called at the end of bootstrap, so a tap that launched the app is not lost), and skips a page they have turned off. `PlannedNotification.destination` is part of the diff, so already-scheduled reminders pick it up. A new kind of reminder needs an id prefix in that mapping. To test in the simulator, `xcrun simctl push <device> <bundle id> payload.json` with `"category"` and the info keys, then long-press the banner (wait for it to appear first).
- **Delete buttons in editors** (`CornerDeleteButton.swift`, `.cornerDeleteButton(...)`): every editor sheet that can delete what it edits (chore, routine, recipe, sleep entry, birthday/anniversary) uses the same red trash button in the bottom-right corner, never a button under Save, and it asks first. It ignores the keyboard so it can't ride over the fields, and the sheet leaves bottom padding so nothing scrolls under it. When Save is pinned in a bar along the bottom (the celebration editor on a narrow sheet) the trash lines up with that bar. Use this modifier for any new editor with a delete. Not changed on purpose: the note editor's Delete Note sits in its own form section away from the toolbar Save, and removing a profile photo sits beside Replace (reversible). The Today Notes card's × asks before deleting and has a 44pt target.
- **Celebration colors** (migration 0030, `family_birthdays.color`): a birthday or anniversary that isn't a household profile has an optional color from the profile palette, chosen with `ProfileColorPickerView` in its editor. Null means pick from the name (`colorForBirthdayName`, ported as `ProfileColors.automatic(forName:)`, with `ios/checks/profile-colors` pinning the two together), so every older row looks as it did. The editor shows the color it would be given and writes it on save. Profile birthdays use the profile's color (set it on the profile), and a row linked to a profile shows the profile's color even if one is stored. `POST`/`PATCH /birthdays` take `color` (refused if not in the palette; left out, as older apps do, keeps what is stored). The dashboard builds its own celebration list, so it maps `color` too; keep the two in step.
- **Colors and dark mode (iOS)** (`HubTheme`, `AccentPalette` in `HubComponents.swift`; the color data and rules are in `Utilities/AccentColors.swift`, Foundation only, checked by `ios/checks/accent-colors`): the ten theme colors are Moss #5F8153 (Moss Deep sage, an earthy green; the name stayed), Azure #56A2DC, Tangerine #F2852C, Blossom #E656A8, Slate #6C7684, Rosewood #B05E6B, Seafoam #46A4A0 (a soft teal), Amethyst #9564CE, Raspberry #F22C4A and Sunflower #F2C02C in dark mode (`AccentColorTable.dark`; Moss's light value is #57764C and Seafoam's #409692), each with a deeper light-mode value (`light`, deep enough to be 3.5 to 1 on white; yellow stays as it is). The names people see (`label`) are not the saved `rawValue`s (sage, ocean, clay, plum, slate, rosewood, teal, indigo, rose, ochre in that order), which are kept because they are stored on devices; a device that saved the removed Meadow (`forest`) falls back to Moss. The app icons (`AppIconOption` in `ThemeSettingView.swift`, one `Beacon<Id>.icon` Icon Composer file each, `Beacon.icon` being the default Moss) are the same tugboat in each of the ten theme colors, named and keyed like the theme (the folder names keep the old ids, except Meadow's `BeaconForest`, which became `BeaconRosewood`). Layers, top first: Cabin Windows, Hull Shading, Hull, Cabin, Smokestack Band, Smokestack, Bulwark Shading, Rear Bulwark, Wave. The hull and the rear bulwark are the only layers that take the theme: each has a `fill-specializations` entry with the theme's light value in the default appearance and its dark value in the dark one, and the gradient shading is a separate white-to-black overlay layer on top (a theme-colored layer would lose its own gradient). Everything else is the same on all ten: cream cabin, gold stack with a deep-ink band, ink windows, and a deep-teal wave (gradient #63AEB2 to #2F7580, "Deep teal, softer"; a navy wave was rejected because it vanishes in dark mode, and slates looked dull beside the themes). The hull's lower edge follows the wave's top edge (lifted about 34 px, with a smoothed bow corner); the cabin's roof slopes about -7.8 degrees and the windows and stack are skewed to match, so keep that angle on any edit. Both shading layers have `"glass": false`. **Icon history:** earlier designs are kept in `ios/IconArchive/` (`01-beacon-sun`, `02-porchlight-house` with its glow script and previews; see its README), so a new design should be archived there before it replaces the bundles. `npm run icons:generate` makes the web favicon, `apple-icon` and the iOS fallback PNGs from `Beacon.icon` (it no longer touches the picker previews). The previews in the picker (`AppIcon<Id>Preview` in `Assets.xcassets`) are 256 px renders made with `ictool` from the Icon Composer app (`ictool X.icon --export-image --output-file out.png --platform iOS --rendition Default --width 256 --height 256 --scale 1`), so re-render them whenever an icon changes. Every chosen color is at least 3 to 1 as text on the dark card, and **any text or icon in the theme color must use `HubTheme.accentText`** (not `accent`/`sage`, which are for fills): it is the accent itself where that already reads at 4.5 to 1 and a lighter (dark mode) or deeper (light mode) shade of it where not (`ColorMath.textShade`), so small labels stay readable in every theme. Text on an accent fill is `HubTheme.onAccent`, whichever of white and near-black has more contrast for that color and mode; `HubTheme.onFill` is for the destructive coral. People's colors (profiles, celebrations) are still stored as the original hex values, so the server, the web settings and every old row are unchanged; `HubTheme.profileColor` shows them as the theme colors (`personColors`: Coral as Raspberry, Blue as Azure, Sage as Moss, Plum as Blossom, Gold as Sunflower, Teal as Seafoam, Lavender as Amethyst, Terracotta as Tangerine, Olive as Rosewood) and `ProfileColors.options` carries the new names. The web settings page still shows the old hex swatches. Choosing the palette is documented in the notes, not code: the finalists were measured by perceptual distance (colors under about 24 apart look alike) and by contrast. **Appearance settings (Settings > Appearance, `ThemeSettingView`):** a Mode row (Automatic, Light, Dark; `AppearanceMode`, applied as `.preferredColorScheme` in `HomeHubApp`), a **True Black** switch, the theme colors as a grid of miniature Today cards, always five across so the ten are two rows on every device (`MiniPage`, drawn at 64 pt wide and scaled to the column's width, with its 12 pt corners and outline applied after the scaling so the selection ring (`MiniPage.cornerRadius` + 3) fits at every size, the grid capped at 130 pt a tile on a wide iPad; drawn from the real `HubTheme` colors and forced into light or dark with `.environment(\.colorScheme, ...)`), and the App Icon row; all are per device (`AppState.appearanceMode`, `usesTrueBlack`, `accentPalette` in UserDefaults) and apply the moment they are tapped. **True Black** (off by default, so dark mode is still charcoal) moves every dark surface down one step: page #000000, cards #1C1C1E, things inside cards #2C2C2E. `HubTheme.canvas/surface/surfaceStrong/tile/tileQuiet` are computed properties that return a different `Color` for each setting; keep them that way, because one dynamic `UIColor` that looked up the flag itself would be resolved once and cached, and the screens would not change when it flipped. Choosing a theme color rebuilds the whole tab tree (`RootView` puts `.id(appState.accentPalette)` on `HubView`, so every static `HubTheme` color is read again), which would throw away any state held in a view; the open Settings pages are therefore kept in `AppState.settingsNavigation` (`SettingsNavigationModel`, shown through `SettingsStack` in both the iPhone tab and the iPad split layout) so you stay on Appearance after picking a color. Any other screen where a theme-color change must not lose your place needs its navigation path held the same way. A small view that draws those colors without reading `AppState` (like `MiniPage`) needs the flag passed in so it redraws. **Dark mode is charcoal by default, never true black unless chosen:** page `#1C1C1E` (`canvas`), cards `#2C2C2E` (`tile`), things inside cards `#3A3A3C` (`tileQuiet`), and text fields use `HubFieldStyle` (the card color) rather than `.roundedBorder`, whose well is black. The tab bar and every navigation stack paint the system background, which *is* black, over the app, so each screen that sits directly in one calls `.hubPageBackground()` (Today, Settings and Meals roots, Today's pushed pages, and any Form or List after `.scrollContentBackground(.hidden)`); a new screen needs the same or it shows black. Text on a colored fill uses `HubTheme.onAccent` (white in light mode, near-black on the bright dark-mode accents and on yellow), `HubTheme.onFill` for the destructive coral, and `HubTheme.readableText(on:)` for profile colors, never a hard-coded `.white`. People's colors (profiles, celebrations) are still stored as the original muted hex values so the server, the web settings and every old row are unchanged; `HubTheme.profileColor` shows them as livelier colors (`vividProfileColors`), so add a new palette color to both lists.
- **Cropping photos before upload (iOS):** the two photo pickers (a person's photo in `ProfilePhotoUploadView`, the family photo in `HouseholdPhotoUploadView`) no longer upload what was picked; they open `PhotoCropView` ("Move and Scale") first. The picked photo is made upright and at most 3000 px (`ProfilePhotoHelpers.cropSource`, so the crop rectangle and the screen agree and a big photo doesn't fill memory), shown behind a cut-out in the shape it will have (`PhotoCropShape`: circle for people, the same rounded square as `HouseholdMarkView` for the family photo) with everything outside the shape dimmed and the outline drawn. Drag to move, pinch or the slider to zoom (1x to 5x), double-tap to reset. The window can never show empty space: that rule and the crop rectangle are `PhotoCropGeometry` (Foundation only, `ios/checks/photo-crop`); `ProfilePhotoHelpers.cropped` cuts the square out and the existing `prepareUploadData` still downsizes and compresses it. The uploaded image is always a square; the shape is only how it is shown. A new place that picks an avatar photo should use the same flow.
- **Crouton import** (`Import from Crouton` in the Recipes menu): the phone reads `.crumb` files (JSON) and sends only their text to `POST /recipes/import/crouton` in batches of 10; `src/lib/recipes/crouton.ts` maps them (units, fractions, ranges, sections, nutrition, tags) and `recipes.import_key` (`crouton:<uuid>`) makes re-imports skip what is already there. Photos are resized on the phone and sent one by one to `POST /recipes/[id]/image` (Vercel Blob; sniffed by content, not by the claimed type). Section headings are `## Heading` lines in ingredients/directions: render them with `RecipeLines.display` and keep them off grocery lists with `RecipeLines.items`.
- **Invite codes can be replaced** (`POST /household/invite-codes` with `which: parent | guest | both`, parents and owners): the old code stops working at once and members are untouched; Settings → Family has a replace button beside each code. Member email addresses are likewise sent only to people who can manage the household (guests get empty strings).
- **Request and refresh cost:** `getCurrentHousehold` returns `hasOwnProfile`, and `ensureMemberProfiles` runs only when it is false (joins create the profile at join time), so a normal request is the session lookup plus one household query. On the phone, `refreshDashboard` re-reads the device's calendars and reminders at most every 5 minutes (weather has its own, longer interval, see **Weather**) (EventKit changes still arrive at once through `observeEventKitChanges`; pull to refresh forces it), and local reminders are synced by difference (`NotificationDiff`) instead of cleared and re-added.
- **Capitalization of text (iOS):** follow Apple's conventions. **Title Case** for anything that names or does something: page and card titles, section headers, buttons and their labels, form-field and toggle/picker labels, navigation titles, segmented and tab labels, and short status headings ("Import Finished"). Lowercase only articles, short conjunctions and prepositions up to three letters ("Rest of the Year", "Time of Day", but "Confirm With Your Password"). Menu and picker **options** and status badges are Title Case too ("Every Day", "15 Minutes Before", "At Time", "Not Enabled", "Import from URL"). **Sentence case** for sentences and messages: descriptions, footers, alerts' messages, placeholders and example text in text fields ("Add a note", "Feed the dog"), empty states and status sentences ("Not planned", "All set", "Signed out", "Can manage"), notification titles and text only VoiceOver reads. Form sheets that discard on exit use "Cancel", not "Close". A celebration's type name in a button or title uses `CelebrationKind.capitalizedNoun` ("Add Birthday"); `noun` stays lowercase for sentences. Default routine step names stay sentence case (they are tasks the family edits). Use "&" in titles as iOS Settings does ("Calendar & Reminders"). **Consistency rules:** one area has one name per place (Food: sidebar, Today card and Layout all say Food; its first tab and that tab's heading say Weekly Plan; the Today cards keep a page's name unless noted, e.g. Schedule opens Calendar). Device-permission status is always Allowed, Not Asked, Denied or Restricted (`settingsLabel` on the calendar and reminders access enums, `DevicePermissionState.label` on Privacy & Access; the Settings list summarizes as Allowed, Partial, Not Asked or Denied). A section header or card title must not repeat the navigation title above it. Week ranges are formatted only by `MealPlanHelpers.weekRangeLabel` ("Oct 5 – 11", "Sep 28 – Oct 4"). A row action in a card or a list row is a labeled button ("Edit Chore", "Edit"), not an icon alone; a list header does not carry a count in parentheses. The add button on Celebrations is named for the page (`CelebrationNaming.currentSingular`: "Add Celebration" or "Add Birthday"). There is no shared string table, so when changing a label search for every copy of it.
- **Showing failures:** call `appState.report(error)` for anything that fails while someone is using the app (it shows a banner from `RootView` for a few seconds). `appState.errorMessage` is only drawn by Today when there is no dashboard at all, so a failure set there with a dashboard on screen says nothing. A pull to refresh that fails also reports that the data is the last saved copy. Destructive settings actions (sign out, removing a guest, resetting the layout) ask first. Timers in views use `onTick(every:)` in `DashboardView.swift`, not `Timer.publish` in a view body.
- **Where the session lives (iOS):** the sign-in cookie is the whole credential, so it is kept in the Keychain (`SessionCredentials`, `Services/SessionCredentials.swift`), not in the cookie storage (a plain file in the app's folder that device backups include). `APIClient` uses a session with cookies turned off, attaches the saved `Cookie` header itself (only to the server it was issued by) and records `Set-Cookie` changes from every response, including a refreshed or cleared session. The Keychain item is `AfterFirstUnlockThisDeviceOnly`, one per server origin. The first launch of this version moves an existing sign-in out of the cookie storage so nobody is signed out; on a fresh install it clears anything the Keychain still holds from a previous install (the Keychain survives deleting an app). The Keychain needs the app's `application-identifier` entitlement, which Xcode adds to any signed build; an unsigned build (`CODE_SIGNING_ALLOWED=NO`, as used for quick compile checks) cannot save to it (status -34018, logged as "could not save the session"), so test sign-in persistence with a normal Xcode build. `ios/checks/auth-session` covers it with an in-memory store.
- **Signing in, out and expiry (iOS):** only a clear "no session" answer from `/api/auth/get-session` (a 200 with `null`) signs the app out at launch (`AuthService.restoreSession`); no connection, a timeout, a server error or a Wi-Fi login page leaves the person signed in. The app opens straight to the offline copy with the saved user (`HomeHubLocalStore.saveUser`) and checks the session behind it. A 401 from any refresh (`APIError.unauthorized`) goes through `AppState.handleSessionExpired` back to sign-in with a banner. The sign-in service (Better Auth, `/api/auth/*`) refuses a cookie-bearing request with no `Origin` header, and a POST with no JSON body (415), so `APIClient` sends the server's own origin on those paths, sign-out sends `{}`, and sign-in and sign-up clear any old cookie first. Sign-out also forgets the cookie when the server can't be reached. The sign-in service's errors are `{"message"}`, Tugboat's own are `{"error"}`; `serverErrorMessage` reads both. `ios/checks/auth-session` runs the real `AuthService` against a stubbed server.
- **Photos in lists (iOS):** use `RemoteImage` (`RemoteImageLoader.swift`), not `AsyncImage`. It keeps a 300 MB disk cache (the system's default is about 10 MB and won't hold a photo that size, so every card and filter change downloaded them again), decodes at the size shown (`ImageDownsampling`; stored photos are up to 1600 px, about 7 MB decoded), keeps decoded images in a bounded cache and lets go of a card's image when it scrolls away. `RemoteImage` also owns its touch area: a photo scaled to fill is bigger than its frame, and `.clipped()` hides the overflow without stopping it taking touches, so a tall photo used to sit invisibly over the filter chips and Add button above its card (the "Alternatives filter can't be switched off" bug). Any new view that fills and clips something needs `.contentShape(Rectangle())` (or the photo `.allowsHitTesting(false)` over a flexible base, as `RemoteImage` does). Recipe filter chips toggle with `RecipeTagHelpers.togglingFilter`, which uses the tag as shown; `toggling` re-spells it for the editor and would leave a filter no chip could switch off.
- **Default Today layout (iOS):** Settings → Layout → Today Cards has Set as Default and Restore Default. `TodayLayoutDefault` (`Utilities/TodayLayoutDefault.swift`) captures the card order, sizes and which cards are on for the device type being edited (iPhone or iPad & Mac) and puts them back; it is kept in UserDefaults per signed-in person and device type (`TodayLayoutDefaultStore`), not on the server. It changes only the Today cards (not Navigation or Food), keeps cards added to the app since it was saved, and ignores cards or sizes that no longer exist. Which cards are on is shared by every device, so restoring changes it everywhere. Reset layout is separate and goes back to the app's own arrangement. `ios/checks/today-layout-default` covers it.

There is deliberately **no wiggle**: it was built (a repeating rotation per card, then flattening each card with `drawingGroup()` to make it cheap) and dropped because it was jittery on a phone however it was driven (alternate cards stuttered when they were started two ways, a restarted `repeatForever` animation kept the old one running so tilts piled up to 10 degrees, and a clock-driven version was never judged smooth enough), so don't add it back casually. Swapping is damped (`swapIfOverAnotherCard`): nothing swaps while the finger is inside the dragged card's own landing cell, and after a swap the finger must travel 30 pt before the next (plus a 0.22 s pause), because a swap reshuffles the first-fit packing and can leave a still finger over a different card, which swapped again and again, so the other cards bounced back and forth under a held card. While a drag is under way `previewOrder` holds the order; `TodayLayoutEditing` (checked in `ios/checks/today-editing`) has the rules: dragging onto a card puts the dragged card in its place, saving keeps turned-off cards where they were (`storedOrder`), `addableCards` leaves out Weather and cards whose module is off. The narrow single-column iPad fallback (under 520pt wide) has no edit button, only Settings. `ios/checks/dashboard-grid` pins the sizes, the packing and the column count. `RemoteImage` looks in the image cache when its state was just cleared, so a card that is rebuilt (entering and leaving edit mode does that) doesn't flash a photo back to its initial.
- **Unified Today cards (every card)** (`Views/Dashboard/TodayCard.swift` and one `<Name>TodayCard.swift` per card): one card design for all nine cards and both devices, with a real layout for each of Small, Medium and Large, so the Today page can be arranged to show what a family wants to see. `TodayCardFrame` is the shared frame (22 pt corners, 14 pt padding, header with icon, title and a chevron that opens the page, the tile background), and `TodayCardSmallBody`, `TodayCardHeadline` (the big phrase and its caption), `TodayCardSummaryLine` ("2 left · 1 done"), `TodayCardSection` (a named group of rows), `TodayCardEmptyNote` and `TodayCardDayChip` are the pieces inside it; rows are `DashboardRow` inside `WholeRowsGrid`, which fits whole rows and says "+N more". **The pattern:** **Small** = headline + one line + at most a progress bar or avatars, and the whole card is one button that opens the page (no actions); **Medium** = summary line + today's rows (tickable), in as many columns as the width allows; **Large** = summary line + two named sections or columns (one above the other at Accessibility text sizes). Check any new two-column page on an iPad mini in portrait.
- **iPad dashboard row height** (`DashboardCardLayout.rowHeight`) is the whole screen's height (less the greeting and a strip for the edit button) divided by the grid's total row count, so the cards fill the screen. A Large card is two rows tall (`height(for:)`); Small and Medium are one. It is unrelated to any card's own content, so a card with more rows of content than fits shows "+N more" unless its content has its own `ScrollView` (every dashboard card does now; Meals was the one exception until it started clipping Dinner). `DashboardRowHelpers.swift` holds two small rules used across cards: don't repeat a value that's identical on every row (a native Reminders item's `category` is really just its Reminders list's name; a schedule row's calendar name is only worth showing once more than one calendar is in play).
- **Snacks** are household-wide by default: one tap marks a snack eaten for everyone. `households.snacks_per_child` switches to per-child tracking, where `snack_completions.profile_id` records which child ate it (`""` is the household-wide row, so it can sit in the primary key). Per-child only applies while the household has a child profile; with none it falls back to household-wide. The dashboard's `snackEaten` stays a flat label list for older app versions (in per-child mode a snack counts once every child has had it), and `snackCompletions` carries who ate what. The rules are in `snackEatenLabels` (`src/lib/meals/snacks.ts`) with `SnackHelpers.swift` as the iOS copy. A child's snack circle (`SnackChildChips`, used on Today and the Snacks page) shows their profile photo when they have one (`ProfilePhotoHelpers.hasPhoto`): faded with a thin ring in their color until they have had it, then full color with a solid ring and a small check badge; with no photo it is their color with their initial, and a check once eaten. With per-child tracking on, the Snacks page shows how many of today's snacks each child has had (`SnackHelpers.eatenCounts`, a bar in the child's color): inside the Today's snacks card beside the list, or as a Progress section above the list when the page is narrow. The Snacks lists use `.scrollContentBackground(.hidden)` with `.hubPageBackground()` and `HubTheme.tile` rows, like Settings, so dark mode is charcoal rather than black.
- **Rate limiting and headers:** `checkRateLimit` (`src/lib/rate-limit.ts`) is one atomic upsert, so a burst of simultaneous requests cannot all slip under the limit; keep it a single statement. Security headers (nosniff, frame denial, referrer and permissions policy, and a CSP with only `frame-ancestors`, `base-uri`, `object-src`, `form-action`) are set for every path in `next.config.ts`. There is deliberately no `script-src`: the root layout has an inline theme script. `e2e/headers.spec.ts` checks real responses.
- **Demo data for App Review** (`scripts/seed-demo.ts`, `npm run seed:demo`, text for App Store Connect in `ios/APP_REVIEW_NOTES.md`): takes `DEMO_OWNER_EMAIL`/`DEMO_OWNER_PASSWORD` and `DEMO_GUEST_EMAIL`/`DEMO_GUEST_PASSWORD` from the environment, creates the accounts if missing (an existing one keeps its password, and both are marked email-verified), and rebuilds the households from scratch every run with dates relative to today, so run it again right before submitting. The owner is the only member of "The Rivera Family" so App Review can try account deletion; the guest belongs to an identical second household run by a hidden owner. It refuses a database that isn't a local file unless given `--yes`, never touches a household with a non-demo member, and prints the host it is writing to. Keep it in step with the schema when tables or columns change.
- **Legal pages:** the privacy policy and terms (`src/app/privacy`, `src/app/terms`) take the app's name and the public contact address from `src/lib/app-info.ts` (`APP_NAME`, `CONTACT_EMAIL`); change them there when the app is renamed or gets its own address (the iOS app, its Info.plist display names, the email templates and the web pages also say the name: search for it when it changes). The policy lists what is stored, what stays on the device, location going to Apple Weather, and the providers (Vercel, Turso, Resend, Apple), so update it whenever data practices change, and keep it matching the privacy manifest (`ios/HomeHub/PrivacyInfo.xcprivacy`) and the App Store privacy answers.
- **Web** (`src/app/`): the only product pages are sign-in, onboarding, settings (household, profiles, members, photos), email confirmation, privacy and terms. Everything else is the iOS app: `(hub)/[section]/[[...rest]]/page.tsx` answers the old section addresses (`/dashboard`, `/calendar`, `/meals/recipes`, … and the one a guest is sent to) with an `IOSOnlyPage`, and anything else is a normal 404. There is no PWA manifest and no wall clock: those belonged to the web-app days. Real web pages are sign-in, onboarding, settings (household, profiles, members, photos), privacy, and terms. Server actions in `src/app/actions.ts` cover only household, profile, and photo management.
- **iOS** (`ios/HomeHub/`): `Models` mirror the schema, `Utilities` port logic from `src/lib`, `Services` hold the API client and on-device integrations (EventKit calendars, Reminders for groceries, WeatherKit, local notifications), `ViewModels` and `Views` are per module. The only extension is the Sleep Live Activity (`ios/HomeHubLiveActivity/`); the Home Screen widget was removed. The Xcode project is generated: after adding or removing Swift files, run `python3 ios/generate-xcode-project.py`. Its object IDs come from names, so regenerating leaves the file unchanged (and an Xcode scheme saved in `xcshareddata` stays valid); keep new IDs name-keyed (`uid("name")`), never random. **Versions:** `MARKETING_VERSION` (0.1 for the first TestFlight build) and `BUILD_NUMBER` are set at the top of the generator and read by both Info.plists through build settings; raise `BUILD_NUMBER` for every upload to App Store Connect (the app and the Sleep extension must match), then regenerate. Archive and upload with `/Applications/Xcode.app`, not `Xcode-beta` (Apple refuses beta toolchains). See `ios/README.md`.
- **Sleep Live Activity:** `HomeHubLiveActivity/` is a widget extension target (bundle id `com.porchlighthome.app.liveactivity`, defined in `ios/generate-xcode-project.py`) that draws the lock screen and Dynamic Island timer. `SleepActivityAttributes.swift` is compiled into both the app and the extension, so keep it free of app-only types. `SleepLiveActivityManager.sync` reconciles one activity per active sleep and runs after every dashboard refresh and Sleep page load; activities are started locally (no APNs), so another device's nap shows up here only on the next refresh.
- **Weather (iOS, WeatherKit):** `NativeWeatherService` reads WeatherKit for the device's location; it needs the `com.apple.developer.weatherkit` entitlement and `BEACON_WEATHERKIT_ENABLED` in Info.plist (both on), which only a paid team can provision (the project builds with team `25TTL3SG99`, bundle id `com.porchlighthome.app`). Debug builds with the flag off show a sample reading. A reading is reused for an hour (`automaticRefreshBackoff`; a failed attempt with nothing to show retries after 15 minutes), and pull to refresh fetches regardless. The header readout (`WeatherHeaderReadout`) opens `WeatherDetailsPanel` (a popover, also on iPhone) with the day's details and, at the bottom, the Apple Weather mark and an "Other Data Sources" link from `WeatherService.shared.attribution`. Apple requires that attribution wherever WeatherKit data is shown, so any new place that shows weather needs it too.
- **Calendars are on-device only.** The server stores no calendar credentials or events. Anything named `calendarConnections`, `calendars`, or `calendarEvents` in the schema is unused legacy.
- **Deleted groceries are not kept.** The server used to copy every deleted or cleared grocery into `recycle_bin_items`, but nothing could read or restore them, so migration 0028 dropped that table and the write. It also dropped four tables for features that never shipped in the iOS app (`school_subjects`, `school_periods`, `school_schedule_entries`, `notification_preferences`; reminders are scheduled on the device). Don't recreate them without a screen that uses them.
- **Schema changes:** hand-write the SQL in `drizzle/NNNN_name.sql` and add its entry to `drizzle/meta/_journal.json` (with a `when` greater than the previous one). Do not run `db:generate`: snapshots stop at 0007, so it would emit a bogus diff. Every statement in a file needs `--> statement-breakpoint` between it and the next, or only the first statement runs. `vercel.json` runs `db:migrate` before the build for production deploys only (`VERCEL_ENV=production`), so previews never touch the database. Migrations are the only way the schema changes: there is no runtime patching. `node scripts/check-migrations.mjs` (read-only) shows what `db:migrate` would run against `TURSO_DATABASE_URL`.

Checks: `npm run typecheck`, `npm run lint`, `npm test`, and an Xcode build of the `HomeHub` scheme for any iOS change.

## Cursor Cloud specific instructions

Standard commands live in `package.json` and `README.md` ("Checks" section); the notes below only cover non-obvious setup for running the backend in this VM.

- `.env.local` is gitignored, so it does not persist across fresh VMs. Create it before running the dev server: `cp .env.example .env.local`. `TURSO_DATABASE_URL` defaults to `file:local.db` and `BETTER_AUTH_SECRET` has a dev fallback, so the app boots even with empty secrets, but a real `.env.local` avoids surprises.
- The local SQLite DB (`local.db`) is gitignored and not created by `npm install`. Run `npm run db:migrate` once before `npm run dev` (migrations are intentionally kept out of the startup update script).
- Run the dev server with `npm run dev` (Turbopack) on port 3000. Do not use `npm start` for development. `npm run build:with-migrate` runs `db:migrate` first; plain `npm run build` does not.
- E2E tests (`npm run test:e2e`) use Playwright and need browsers installed first (`npx playwright install`, and `npx playwright install-deps` if system libs are missing). The Playwright config auto-starts its own dev server against `file:e2e.db`, so no manual server is needed for e2e.
- Core hello-world flow: open `http://localhost:3000` → Sign in → "Create an account" → complete `/onboarding` by creating a household → lands on `/settings`. Vercel Blob photo upload is an optional integration needing external credentials and is not required for local core testing.
